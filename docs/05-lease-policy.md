# 05 · 租约与策略机

> 上一章解决了"平时省电"，这一章解决"要用的时候怎么拿到卡"。  
> 答案不是拦截 `open()`，而是**在 `open()` 之前就把决定做完**。

## 1. 两个状态

| 状态        | 节点位置                       | 系统服务可见 | 功耗    | 谁在用        |
| --------- | -------------------------- | ------ | ----- | ---------- |
| **SLEEP** | `/dev/b60/{card,render}`   | ✗      | ~8 W  | 容器（直通路径）   |
| **WORK**  | `/dev/dri/{card,renderD*}` | ✓      | ~42 W | 系统级任务 + 容器 |

只有两个状态、只有一件事在变：**节点在哪个目录**。  
没有第三种中间态，也没有"半掩藏"。

## 2. 策略（policy）

| 策略         | 行为                     | 适用            |
| ---------- | ---------------------- | ------------- |
| `auto`（默认） | 有租约 → WORK；无租约 → SLEEP | 日常            |
| `masked`   | 强制 SLEEP，忽略租约          | 排障 / 需要绝对低功耗时 |
| `exposed`  | 强制 WORK                | 长时间系统级转码      |

```bash
curl -s -X POST http://127.0.0.1:41966/api/policy \
     -H 'Content-Type: application/json' -d '{"policy":"auto"}'
```

## 3. 租约（lease）

租约是一次**有期限的暴露窗口**，落在 SQLite 里，进程重启不丢。

```bash
curl -s -X POST http://127.0.0.1:41966/api/lease \
     -H 'Content-Type: application/json' \
     -d '{"ttl":900,"reason":"示例：影视转码","who":"cli"}'
# → {"id":"a1b2c3d4", ...}

curl -s -X DELETE 'http://127.0.0.1:41966/api/lease?id=a1b2c3d4'
```

| 字段       | 约束                             |
| -------- | ------------------------------ |
| `ttl`    | 服务端夹在 `[30, 3600]` 秒           |
| `reason` | 面板上显示给人看                       |
| `who`    | `b60-run` / `cli` / `api`，用于归因 |

**为什么用租约而不是"检测到调用就切"？**  
因为"调用"发生在 `open()`，而 `open()` 在内核里——用户态没有可靠的拦截点  
（`inotify` 看不到 `open`，`fanotify` 需要全盘挂载且与 Docker 冲突，`LD_PRELOAD` 只能影响被注入的进程）。  
所以把决策点**前移到任务启动时**：启动器先申请窗口，再启动任务。

## 4. 防抖

切换会重启系统服务（释放旧 fd），代价不小，所以策略机带两级防抖：

- 目标态必须**连续保持 15 秒**（`SWITCH_DEBOUNCE_S`）才执行；
- 两次切换之间至少隔 15 秒；
- 每 3 秒跑一次决策（`_dispatch_once`）。

这避免了"租约刚建立又释放"导致的来回抖动。

## 5. 污染看门狗

掩藏态下如果 L1 驻留跌破 **40%** 且存在持卡者，连续 3 次采样（约 45 秒）后判定为"污染"：

```
WARN  掩藏态下 L1 仅 12%（阈值 40%），持卡者：容器 foo、systemd xxx
```

- 默认只告警，不自动处置（`AUTO_EVICT=0` 可完全关掉自动驱逐）。
- 开启自动驱逐时：重新掩藏（幂等搬移 + 重启系统服务），把新出现的轮询者踢出去。
- 典型触发场景：udev 重建了 `/dev/dri` 节点、或某个新装的服务开始扫 GPU。

## 6. 消费者画像

面板上的"谁在用"不是猜的：

```
pid ──/proc/<pid>/cgroup──▶ 容器名 / systemd 单元 / 宿主进程
  └──/proc/<pid>/fdinfo/*──▶ drm-engine-* 增量 ──▶ 干活中 / 仅识别
```



| 角色           | 判定           | 对功耗的影响    |
| ------------ | ------------ | --------- |
| 仅识别（idle）    | 打开了节点，引擎占用 0 | 无（链路照样睡）  |
| 干活中（working） | 引擎占用 ≥1%     | 有（链路出 L1） |

工作时段（session）按这个口径记账：占用 ≥1% 开始，连续 30 秒无占用结束。  
所以"谁在什么时候真用过 GPU"是可回看的，不依赖日志人工翻。

## 7. 开机持久化

`state.json` 里存的是**期望状态**（是否掩藏 + 策略）。  
容器启动时自动套用一次，等价于开机脚本；不需要额外 systemd 单元，也不会和容器重启策略打架。

```json
{"mask_enabled": true, "policy": "auto"}
```
