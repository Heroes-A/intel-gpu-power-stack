# 04 · Node masking: why moving `/dev` saves power

> 中文: [04 · 节点掩藏：为什么搬 /dev 就能省电](../04-node-masking.md)

> This is the least "technical-looking" step in the whole project: move two device nodes and
> power drops from 42 W to 8 W. But it has a clear causal chain — and clear boundaries.

## 1. The causal chain

```
System services (sysinfo / resmon / media service) enumerate /dev/dri every N seconds
        │
        ├── B60 visible → open the node → periodic MMIO register reads
        │                              │
        │                              └─ each read = a link transaction → link back to L0
        │                                 → L1 residency broken → ~42 W
        │
        └── B60 invisible → nothing opened, nothing polled
                                       └─ link untouched → enters L1 → ~8 W
```

The key point: **what they enumerate is the `/dev/dri` directory** — not sysfs, not the PCI bus.
So as long as the nodes aren't in that directory, polling stops by itself: no stopping services,
no editing service configs, no hooks.

## 2. The concrete action

```bash
mkdir -p /dev/b60
mv /dev/dri/card0        /dev/b60/card
mv /dev/dri/renderD129   /dev/b60/render
```

- It's a **`rename` within the same filesystem**: same inode, same device number, same permissions.
- Processes that already `open()`ed the node are **unaffected** (an fd points at the inode, not
  the path) — which is exactly why a 31 W transitional reading appears right after masking: old
  fds are still being polled, and power only falls to 8 W once they let go.
- Restoring is just `mv` back. `b60-guard` also corrects `root:render` and `0666` on the way.

> The kernel names of `card0` and `renderD*` can differ across machines.
> `b60-guard` reverse-looks them up via `/dev/dri/by-path/pci-<BDF>-{card,render}` instead of
> hardcoding.

## 3. Why not build a "fake device"

The most intuitive idea: create a fake node inside `/dev/dri` so system services detect something
without ever touching the B60. We tried this seriously three times, and all three were dead ends:

| Approach | Why rejected |
|---|---|
| **CUSE userspace char device** impersonating a DRM node | DRM depends on `mmap` for buffers and command submission, and **CUSE does not support `mmap`**. Even if `open` succeeds, the first `mmap` fails |
| **Forging `/sys/class/drm/` entries** | sysfs is generated by the kernel at device registration; userspace cannot write it. `libdrm` enumerates via sysfs + udev, so a pure `/dev` fake node is invisible |
| **`libdrm`'s upfront validation** | `drmGetDevices2()` compares `stat()`'s `st_rdev` against the udev-recorded `devnum` and discards mismatches. You'd have to forge both `/dev` and the udev database inside an isolated mount namespace — well beyond a "lightweight relay layer" |

How we tested it: build the fake node plus fake udev records inside an isolated mount namespace,
with zero host contamination. `drmGetDevices2()` still returned an empty list.

**Conclusion: in userspace you cannot create a DRM device that the system recognizes but that
doesn't resolve to the real card.**
So we changed the approach — don't forge devices, just **redirect paths**, decoupling
"recognition" from "use" onto two different paths:

- System services: only look in `/dev/dri` → invisible while masked → no polling;
- New projects: mount `/dev/b60/render` directly → always get the real card.

## 4. Boundaries and risks

| Risk | Explanation | Handling |
|---|---|---|
| Card doubles as display output | Masking `card0` removes the GPU from console/desktop | Use only on headless machines; don't mask `card0` where a display is attached |
| udev recreates the nodes | Driver reload / device rebind recreates `/dev/dri/*`, breaking the masked state | `b60-guard` has a pollution watchdog: sees L1 drop + a client appear, re-masks |
| Container started before masking | It mounted `/dev/dri/renderD129`, which disappears after masking (fd stays valid but breaks on restart) | Always mount `/dev/b60/render` (see [06](06-integration.md)) |
| Manual `mv` | Out of sync with `state.json`; next dispatch is misaligned | Operate only through the API / dashboard |
| Nodes return to their place after reboot | `/dev` is tmpfs, reset on every boot | `state.json` persists the desired state and is applied on container start |

## 5. Where the code lives

- Mask / unmask: `src/app.py` → `apply_mask()` / `mask_status()`
- Kernel name reverse lookup: `src/app.py` → `_b60_kernel_names()`
- Pollution watchdog: `src/app.py` → `_watchdog_tick()` / `_evict()`
- State persistence: `src/app.py` → `_save_state_file()` / `_boot_apply()`
